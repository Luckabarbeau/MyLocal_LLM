# 0092 — Live pretraining benchmarks and supervised-token tracking

This is an **opt-in** integration with the existing autoregressive trainer.
It does **not** save or reload a checkpoint for evaluation. The normal
`--save-interval` and end-of-run training-recovery checkpoints are unchanged.

## Enable

From the repository root, add to your **existing working training command**:

```bash
--benchmark-suite ./benchmarks/configs/foundation_live_0092.json
```

When resuming an **old pre-0092 checkpoint**, there is no authoritative stored
cumulative supervised-token total. Recover the actual count from trusted
historical logs and add:

```bash
--benchmark-supervised-tokens-offset <actual_cumulative_supervised_tokens>
```

Do **not** substitute `steps × batch × context`, and do not blindly use the
nominal `tokens_processed` counter. If the offset is omitted, newly measured
supervised tokens begin at zero with provenance `since_0092_only`; intervals
and totals will be local to this resumed segment. New 0092 checkpoints persist
and automatically restore the running counter. Offsets may be omitted on
subsequent resumes and an inconsistent explicit offset is rejected.

> A CLI offset is only for the first resume of a legacy checkpoint. It does
> not rewrite prior logs or silently claim older token accounting was measured.

### First GPU smoke test

Start with a **separate snapshot of your existing recovery checkpoint** and
append the following to a direct copy of your normal training invocation:

```bash
--benchmark-suite ./benchmarks/configs/foundation_live_0092_smoke.json \
--max-run-steps 1
```

Also supply the legacy token offset if necessary. The small smoke suite runs
WikiText on a truncated 512-token subset, a single eight-token greedy
continuation, and five reference texts with eight-token continuations from one
cutoff. The process will still make its **normal end-of-short-run recovery
checkpoint**. That checkpoint is not generated by the benchmarking system.

After inspecting the benchmark output and verifying unchanged resume behavior,
run the full suite on the production command. The production configuration
runs quick reference and generation checks every 250M supervised tokens and
WikiText-2 at 1024 and 4096 every 500M supervised tokens.

## Files and results

- `benchmarks/configs/foundation_live_0092.json`: production example suite.
- `benchmarks/configs/foundation_live_0092_smoke.json`: GPU smoke configuration.
- `benchmarks/tasks/reference_texts_v1.json`: fixed reference texts; edit and
  version as a separate suite when expanding coverage.
- `benchmarks/live_suite.py`: in-process scheduler and evaluation adapters.
- `benchmarks/reference_continuation.py`: teacher-forced token analysis and
  generations from token-aligned cutoffs.
- `benchmarks/live_report.py`: offline HTML and summary CSV.

The benchmark root contains a machine-readable `metrics.csv`, plus per-step
per-benchmark `result.json`. RCA produces `report.html` where users can read
individual token likelihoods and matched cutpoint generations. The full
`result.json` stores token IDs, true-token probabilities/ranks/entropies and
top-k alternatives, along with generated text. No trained weights are written.

The trainer now saves `supervised_tokens_total` and provenance to checkpoint
training state, fills the legacy `tokens_processed` CSV field with its actual
**source-capacity** meaning, and writes supervised-token totals in new-format
main CSVs. Existing 7-column logs are **not** modified mid-stream: an
adjacent `.supervised.csv` sidecar always supplies the unambiguous total.

## Suite schema

The JSON configuration has `version: 1`, `output_root`, `on_error`, and a
`benchmarks` array. Each item specifies `id`, `type`, `parameters`, and
**exactly one of** `every_supervised_tokens` or `every_optimizer_steps`.
Schedules start at the next threshold after attachment/resume. They execute
between completed optimizer updates, never in the middle of accumulation.

Supported initial types:

1. `wikitext` — the established windowed **plain-context** CE/BPB benchmark,
   scored with `return_cache=False` from the live model (not an independent
   model). Full-context results should match a validated standalone
   `--memory-mode plain` run to floating-point tolerance.
2. `generation` — existing prompt suite, the production `TextGenerator`
   interface, token-ID repetition metrics and generated text; uses the live
   weights, constructing a fresh inference cache for each benchmark milestone.
3. `reference_continuation` — teacher-forced true-token probability/rank,
   entropy, top-k predictions; free continuations from selected token cutoffs.
   For the initial `historical_read` integration it deliberately uses the
   **plain 4K context** (history temporarily disabled and restored). Free
   decoding uses a temporary inference KV cache, not a disk checkpoint.

`branch_top_k` lists potential next-token candidates in JSON; **forced-token
branching is not implemented in 0092**. A low reference-token rank is not
proof the leading alternative is incorrect. Decode/re-encode differences at
cutoffs are flagged as `decoded_prefix_retokenized_differently`.

### Operational boundaries

- Benchmarks run **sequentially on the same GPU**; they pause training.
- The temporary disabling of `historical_read` is restricted to the evaluation
  context and is restored in `finally` even on exceptions. The patch does
  not support in-process plain-mode evaluation of other memory integration
  types. No independent 64K historical-memory evaluation is claimed.
- The standard **training RNG generators** remain separate from benchmark
  sampling. NumPy global RNG state is restored, and the original CuPy global
  RandomState object is restored after temporary seeded generation. GPU configuration/graph parity still requires on-device testing.
- Results carry suite/config hash, optimizer step, supervised-token total,
  and the specific cutoff/prompt parameters. Model weights are *not* archived:
  downstream analysis cannot reconstruct an unavailable intermediate checkpoint.
- `on_error: raise` is the default and safest policy. An evaluation failure
  records `error.json` and stops rather than silently continuing after a
  potentially serious CUDA error. A `continue` policy is opt-in.
- Scoring only the first `max_tokens` of a corpus returns `bits_per_byte: null`;
  a truncated corpus cannot legitimately reuse the full-file byte denominator.

## Validation completed before GPU handoff

- CPU unit tests of scheduling, legacy/new log schemas, no checkpoint needed,
  token-rank calculation, history-mode restoration (including a real tiny
  `historical_read` model), and saved cumulative counts.
- A tiny NumPy decoder was run through live WikiText and RCA KV-cache scoring.

**Not yet verified:** production CuPy/BF16 memory peak, exact WikiText parity
at 1024 and 4096 on the real 338M checkpoint, CUDA-graph cache lifetime,
CuPy global RNG-state handling and full production trainer resume with a
legacy checkpoint. Run the smoke configuration before enabling the full suite.
