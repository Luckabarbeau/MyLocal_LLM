- **Status:** accepted for the configuration/checkpoint plumbing; the parallel architecture itself remains **experimental** until the Model B A/B completes, and the LR-sensitivity motivation below is an **unproven hypothesis**.

- **Semantics:** two Model B local/global branch topologies, now named and persisted: **legacy** — the global branch consumes `residual_hidden + local_delta` (sequential coupling; the graph under which every pre-fork Model B checkpoint, including the ~32B-token pretrained artifact, was trained); **parallel** — both branches consume the same pre-attention RMSNorm output `normalized_hidden`, the historical incomplete-hidden cache stores that normalized input, and global attention has no same-block dependency on the local output.
- **Motivation:** investigate whether the original sequential local→global coupling contributes to Model B's unusually strong learning-rate sensitivity. This is a scientific hypothesis driving the fork; it is **not** experimentally established, and a temporary loss increase after forking a pretrained checkpoint is expected and acceptable.
- **Behavior:** `DualResolutionConfig.attention_branch_mode` (`"legacy"` default, validated; unknown values raise). The canonical Model B presets (`dual-resolution-matrix-pool-1024-20l`, `-sparse-`) select `"parallel"`; Model A's `dual-resolution-1024-20l` keeps `"legacy"` deliberately. `ModelConfig(**config.json)` resolves the mode once during deserialization (`_dual_resolution_from_mapping`), and `train_model.py` resolves again (idempotent) before model construction and before writing the next `config.json`, so native training, PyTorch training, incremental inference, the captured CUDA-graph decoder, pooling/cache construction, checkpoint save/load, and the `training_resume_contract` all read one resolved value. `MINI_LLM_MATRIX_POOL_PARALLEL_BRANCHES` remains only as a read-only architectural **override** (never written to `os.environ` by this repository, so it cannot leak between models in one process); if it fires on a legacy checkpoint it rewrites the in-memory configuration and prints the one-time migration warning. The mode reaches the CUDA-graph decoder through the constructed blocks (`__init__` rejects mixed-mode engines), so graph topology is frozen at capture from the same resolved mode. A training operator and its inference adapter can no longer disagree: `DualResolutionAttentionInference.set_weights` raises on branch-mode mismatch. The PyTorch-backend `save_checkpoint` config guard now permits a `config.json` rewrite when the **only** differing leaf is `dual_resolution.attention_branch_mode` (warns); every other mismatch still raises. `training_resume_contract()` gained an `attention_branch_mode` row: a pre-fork contract resumed on legacy is not drift, while any intentional fork appears as a warn-not-block diff recorded in `resume_contract_history`. No unconditional architecture check blocks a legacy→parallel continuation because both topologies have identical parameter geometry, names, counts (348,261,376) and the `model_b_348m_sparse16` identity/`ArchitectureSpec` are untouched — branch mode is deliberately kept out of the geometry fingerprint.

- **CUDA-graph correction and coverage:** the captured `NativeDualBF16CudaGraphDecoder` fix from the entry below stays intact (`dual_shared_input_store` writes the shared normalized input to the pooling history; store kernel and global-Q input selected once at capture by the resolved mode).
