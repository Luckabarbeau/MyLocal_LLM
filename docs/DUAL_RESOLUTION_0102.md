# 0102 dual-resolution attention

## Status

0102 is an **explicit, correctness-first, unfused NumPy/CuPy implementation** of block-compressed dual-resolution causal attention. It is suitable for API, causality, gradient, memory-scaling, and numerical study. It has not yet been shown to be a production-ready GPU implementation: do not make that claim until the benchmark below has been run on named hardware and the resulting timing, VRAM, and numerical data have been recorded.

The implementation is in:

- `mini_llm/ops/dual_resolution_attention.py` (training forward/backward and packed-document metadata);
- `mini_llm/ops/dual_resolution_attention_inference.py` (bounded incremental inference);
- `mini_llm/config.py` (`DualResolutionConfig` and the production-shape preset);
- `mini_llm/model/decoder_lm.py`, `mini_llm/blocks/transformer_block.py`, and `mini_llm/train_extended.py` (model/trainer wiring);
- `mini_llm/inference_model.py` and `mini_llm/inference_state.py` (native cache wiring).

`benchmarks/benchmark_dual_resolution_0102.py` measures the actual operator without constructing a dense token-by-token `T × T` array.

## Architecture

The preset name is `dual-resolution-1024-20l`, constructed by `ModelConfig.dual_resolution_1024_20l()` and accepted by `train_model.py --model`.

| Field | Preset value |
|---|---:|
| Layers | 20 |
| Model width `d` | 1,024 |
| Dense SwiGLU width | 4,096 |
| Vocabulary | 32,768 |
| Tied embedding/output matrix | yes |
| Query heads `Hq` | 16 |
| KV heads `Hkv` | 4 |
| GQA group size | 4 query heads/KV head |
| Head dimension `Dh` | 64 |
| Main attention scale | `1/sqrt(64) = 1/8` |
| RoPE base | 1,000,000 |
| Context | 65,536 |
| Hierarchical memory / configured sparse heads | disabled / `None` |
| FFN | dense SwiGLU, not MoE |

Each Transformer layer computes:

1. **Exact local token branch.** Q uses 16 heads; K/V use 4 heads. Every query sees at most the causal 512-token same-document window.
2. **Compressor.** Every complete same-document 128-token block is projected from `d` to `dc`, processed by `compression_depth` bidirectional self-attention layers, reduced to one vector by learned multi-head pooling, then projected back to `d`.
3. **Summary branch.** The block summaries receive dedicated 4-head global K/V projections. Token queries attend only to same-document summaries whose block end is strictly earlier than the query position.
4. **Mixture.** A learned sigmoid gate per query head interpolates `local + gate × (global - local)`. If no legal summary exists, the effective gate is zero, so the output is local.
5. **Output projection.** The 16 query-head contexts are merged and projected to width 1,024.

The compressor is bidirectional **inside one already completed block**. This does not leak future tokens to a query: a block summary is visible only when its end position is strictly less than the query position.

## Causality, packing, and EOS semantics

Training metadata is generated by `build_dual_resolution_metadata(inputs, eos_token_id, block_size)`:

- EOS belongs to the document it terminates.
- The token after EOS starts a new document with document position zero.
- Blocks restart at each document boundary.
- Only complete blocks are summarized; incomplete tails are not emitted.
- Local attention requires equal document IDs, `key_position <= query_position`, and distance `< local_window`.
- Summary attention requires equal document IDs and `block_end_position < query_position`.
- `dual_resolution_loss_mask(inputs, eos_token_id)` clears the loss position whose **input** is EOS. With ordinary shifted targets, this removes the otherwise cross-document target immediately following EOS. A supplied mask is multiplied by this EOS mask.

Native incremental inference stores local K/V, summary K/V, and the incomplete normalized block independently for each layer and batch row. If `InferenceModel.create_generation_state(..., eos_token_id=...)` is called with an EOS ID, EOS remains in the old document and the row resets before the next token. The current `inference.py` wrapper creates state without passing `eos_token_id`; ordinary generation stops when EOS is sampled, but callers that stream multiple packed documents through one state must use the lower-level API and pass it explicitly.

## Configuration contract

`DualResolutionConfig` defaults are:

| Field | Default | Constraint / role |
|---|---:|---|
| `enabled` | `False` | must be `bool` |
| `block_size` | 128 | positive; context must be divisible by it |
| `local_window` | 512 | at least and divisible by `block_size`; no larger than context |
| `compression_dim` | 512 | positive; divisible by `compression_heads` |
| `compression_heads` | 8 | positive; default compressor head dimension is 64 |
| `compression_depth` | 1 | config validation requires positive; operator also accepts zero when constructed directly |
| `compression_block_chunk` | 64 | maximum number of independent 128-token blocks handled per compressor attention GEMM; bounds temporary scores |
| `max_blocks` | 512 | positive; context cannot exceed `block_size × max_blocks` |
| `global_query_chunk` | 64 | positive; bounds token-query score rectangles |
| `recompute_attention_probs` | `True` | recompute local/global/compressor softmax probabilities during backward; `False` retains them for debugging |

When enabled through `ModelConfig`, dual resolution cannot be combined with `memory_context.enabled` or a non-`None` `attention_layers`. The preset also clears `full_history_layers`. Standard model fields such as vocabulary, layer count, widths, heads, RoPE, precision, and initialization remain configurable through `ModelConfig`; no dedicated CLI overrides are currently exposed for the dual-resolution subfields, so changing them programmatically requires `dataclasses.replace`.

Incremental inference currently imposes additional implementation bounds: `block_size <= 128`, `local_window <= 512`, and `max_blocks <= 512`.

## Parameter counts

The parameter estimator has been corrected to count the actual registered
arrays, including dedicated global K/V projections and the pooling query and
normalization scale. The following counts correspond to the full 20-layer
preset, holding the compression head count at 8:

| Compression width `dc` | Trainable parameters |
|---:|---:|
| 256 | **368,173,056** |
| 512 (default) | **406,199,296** |
| 1,024 | **537,302,016** |

The estimates have been checked against model parameter-array counts at smaller
instantiated widths by `tests/test_dual_resolution_0102.py`.
The 512-wide compressor is approximately 406M parameters, **not 338M**.
Width 256 is the closest of these presets to the original 338M parameter budget.

`recompute_attention_probs=True` changes only the backward-cache strategy, not
the trained parameters or attention equations. It does not change checkpoint
shapes, and can be turned off for numerical debugging with a configuration
replacement. Backward recomputes each masked local/global softmax from cached
Q/K and compact document metadata, and each block compressor softmax from its
cached Q/K. The two implementations are checked against each other for complete
forward outputs, input gradients, and parameter gradients.

The compressor attention GEMMs are further chunked by `compression_block_chunk`
(default 64), rather than forming all 512 block score matrices at once. At
65K, 8 compressor heads, block size 128, and FP32 probabilities, a 64-block
chunk forms approximately **32 MiB** of score elements instead of **256 MiB**
for all 512 blocks. Chunking affects neither attention semantics nor trainable
parameters. Tests compare chunk size 3 versus 64 for both retained and
recomputed probabilities, including every parameter gradient.

## Score workload and complexity

Let:

```text
T  = context length
S  = block_size = 128
W  = local_window = 512
C  = global_query_chunk = 64
M  = T / S complete blocks for one unbroken document
Hq = 16, Hkv = 4, GQA group = 4, Dh = 64
Hc = compression_heads = 8 by default
D  = compression_depth = 1 by default
```

Although storage groups Q by 4 KV heads, each of the 16 query heads produces scores. The implementation's actual score-element formulas are:

```text
local rectangular work = Hq × Σchunks qc × (query_stop - max(0, query_start-W+1))
local valid scores      = Hq × Σp=0..T-1 min(W, p+1)
global rectangular work = Hq × T × M
global valid scores     = Hq × S × M(M-1)/2
compressor attention    = D × M × Hc × S²
compressor pooling      = M × Hc × S
```

The local and global rectangular counts include masked score slots actually formed by the chunked implementation. For a single full document, the valid global formula follows from strict `block_end < query_position`. Compressor heads have dimension `dc/Hc` (64 at the defaults), with scale `1/sqrt(dc/Hc) = 1/8`.

Total score work is

```text
O(Hq T W + Hq T²/S + D Hc T S + Hc T)
```

so the summary branch is still quadratic in `T`, reduced by the block factor `S`; this is not linear attention. Query chunking bounds an individual local/global token score rectangle, and no dense token `Hq × T × T` tensor is allocated. The compressor processes at most `compression_block_chunk` completed blocks in each GEMM and materializes per-block `Hc × S × S` probabilities. With the default probability-rematerialization setting, the full local, global, and block self-attention probability arrays are **not retained** for backward; they are recomputed from cached Q/K when needed. Pooling probabilities are still retained because their memory cost is small. Other hidden activations and projections are still retained, and a full 20-layer 65K run may need block activation checkpointing.

At `T=65,536`, defaults produce:

| Score family | Elements |
|---|---:|
| Local chunk rectangles | 600,580,096 |
| Local causally valid | 534,777,856 |
| Global chunk rectangles | 536,870,912 |
| Global strictly valid | 267,911,168 |
| Compressor bidirectional | 67,108,864 |
| Compressor pooling | 524,288 |
| Implementation total | 1,205,084,160 |
| Dense `16 × T × T` comparison (not allocated) | 68,719,476,736 |

**Old retained-probability comparison:** storing one FP32 probability per implementation score element would require approximately 4.82 GB per attention layer at 65,536. The default rematerialization mode avoids that persistent probability cache, but still materializes chunk-sized probabilities and block-compressor matrices **transiently**, and retains other projections and activations for backward. Consequently, the 16 GB training-memory constraint is not yet resolved or GPU-validated. Measure peak VRAM under the actual training configuration, and prefer whole-block activation checkpointing for large contexts.

## Benchmark output and commands

The benchmark defaults to batch 1 and contexts `1024,2048,4096,8192,16384,32768,65536`. Use `--compression-block-chunk 64` to control the compressor's peak score allocation. Use `--retain-attention-probs` only for a debugging comparison on small contexts; it restores the old high-memory backward cache. The benchmark JSON reports `recompute_attention_probs` explicitly. It reports:

- estimator parameter counts for `dc=256/512/1024` and the selected configuration;
- local/global/compressor/pooling score workload split;
- forward, backward, and end-to-end median/min/max time and tokens/s;
- CuPy pool used/reserved bytes before and after phases, when available;
- the equivalent FP32 probability-cache size **if rematerialization were disabled** (a diagnostic comparison, not the default retained memory);
- optional single-layer native sequential prefill, decode, and cache metrics.

It never intentionally creates dense `T × T` storage. `--skip-backward` omits backward/end-to-end, and `--skip-inference` omits incremental metrics.

### Focused correctness and regression checks

A dedicated `tests/test_dual_resolution_0102.py` module now exercises
parameter accounting, strict completed-block causality, packed EOS boundaries,
compressor pooling gradients, full training/inference equivalence, checkpoint
round trips, and rematerialization/chunking equivalence.

```bash
MINI_LLM_BACKEND=numpy python -m pytest -q tests/test_dual_resolution_0102.py
MINI_LLM_BACKEND=numpy python benchmarks/benchmark_dual_resolution_0102.py \
    --validate-only --skip-inference
```

These CPU tests do **not** replace GPU FP32/BF16 kernel validation or a
full 20-layer peak-VRAM training run.

```bash
MINI_LLM_BACKEND=numpy python benchmarks/benchmark_dual_resolution_0102.py \

    --validate --skip-backward --skip-inference --warmup 0 --repeats 1 \
```

## Short training and native inference

Training requires compatible packed shards and tokenizer. This one-update command is an installation/memory smoke test, not a useful training schedule and not proof of GPU production readiness:

```bash
export MODEL_SHARDS=/path/to/compatible_32k_packed_mixture
export RUN_DIR=/path/to/dual_resolution_0102_smoke
mkdir -p "$RUN_DIR/checkpoint" "$RUN_DIR/logs"

MINI_LLM_BACKEND=cupy python -u train_model.py \
    --model dual-resolution-1024-20l \
    --objective ar --precision bf16-mixed \
    --runtime-profile consumer-gpu \
    --mixed-shard-root "$MODEL_SHARDS" \
    --batch-size 1 --grad-accum-steps 1 \
    --gradient-accumulation-weighting supervised_tokens \
    --optimizer hybrid-muon \
    --total-steps 100 --max-run-steps 1 --warmup-steps 10 \
    --val-interval 100 --val-steps 1 \
    --save-interval 1 --log-interval 1 \
    --checkpoint-dir "$RUN_DIR/checkpoint" \
    --log-file "$RUN_DIR/logs/train.csv"
```

A successfully written native checkpoint can use the bounded dual-resolution KV/summary state through the normal native CLI:

```bash
MINI_LLM_BACKEND=cupy python inference.py \
    --checkpoint "$RUN_DIR/checkpoint" \
    --runtime-profile gpu-fast --backend kv-cache \
    --max-context 65536 \
    --prompt "Explain why strict causal masking matters:" \
    --strategy top-k --top-k 40 --temperature 0.8 \
    --max-new-tokens 128
```

The reference full-prefix backend is not the intended long-context path. Preserve the checkpoint's tokenizer/config pairing, and measure prompt prefill, warmed decode tokens/s, cache memory, and output sanity on the target GPU before describing deployment readiness.
