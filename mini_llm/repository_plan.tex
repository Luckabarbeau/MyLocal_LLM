\section{Purpose of the repository}

This repository is meant to be a learning platform for building a small modern
\textbf{large language model (LLM)} from the ground up while keeping the mathematics,
the matrices, and the numerical flow visible.

The central idea is:

\begin{quote}
Every important part of the model should be inspectable as explicit matrices,
explicit tensor operations, and explicit backward derivatives.
\end{quote}

The project is therefore \emph{not} primarily about obtaining the strongest model
possible. Instead, it is about understanding:

\begin{itemize}[leftmargin=1.5em]
    \item how text becomes tokens,
    \item how tokens become vectors,
    \item how \textbf{Transformer} blocks propagate information,
    \item how \textbf{attention} works,
    \item how residual connections work,
    \item how the next-token prediction loss is formed,
    \item how gradients move backward through the model, and
    \item how optimization updates the matrices.
\end{itemize}

\section{Main design philosophy}

The repository follows the following rules.

\subsection*{Rule 1: explicit numerical objects}
All trainable weights should appear as visible matrices, usually through a small
\texttt{Parameter} class with:
\[
\texttt{data}, \qquad \texttt{grad}.
\]

\subsection*{Rule 2: explicit forward pass}
Each module should compute its forward operation with explicit tensor contractions,
for example:
\[
Q = XW_Q,\qquad K = XW_K,\qquad V = XW_V,
\]
rather than hiding the operation behind a high-level neural-network framework layer.

\subsection*{Rule 3: explicit backward pass}
Each module should also contain its own hand-derived backward pass.
For example, if
\[
Y = XW,
\]
then the backward formulas are:
\[
\frac{\partial L}{\partial W} = X^\top \frac{\partial L}{\partial Y},
\qquad
\frac{\partial L}{\partial X} = \frac{\partial L}{\partial Y}W^\top.
\]

\subsection*{Rule 4: CPU first, GPU second}
The same code should run with:
\begin{itemize}[leftmargin=1.5em]
    \item \textbf{NumPy} for a clear \textbf{central processing unit (CPU)} reference implementation,
    \item \textbf{CuPy} for \textbf{graphics processing unit (GPU)} acceleration.
\end{itemize}

\subsection*{Rule 5: verify before scaling}
Every operator should be tested numerically before being integrated into a larger model.
In practice this means:
\begin{itemize}[leftmargin=1.5em]
    \item directional derivative checks,
    \item finite-difference tests,
    \item shape checks,
    \item causality checks for attention,
    \item and small overfitting experiments.
\end{itemize}

\section{Model overview}

The full model will be a decoder-only Transformer for next-token prediction.

\subsection{Input text and tokenization}
A raw text sequence such as
\[
\texttt{"The fluid velocity increases near the wall."}
\]
is converted to discrete token identifiers using a tokenizer such as \textbf{byte-pair encoding (BPE)}:
\[
[t_0, t_1, \dots, t_{T-1}].
\]

\subsection{Embedding}
Each token identifier is converted into a vector through an embedding matrix
\[
E \in \mathbb{R}^{V \times d_{\text{model}}},
\]
where:
\begin{itemize}[leftmargin=1.5em]
    \item \(V\) is the vocabulary size,
    \item \(d_{\text{model}}\) is the model dimension.
\end{itemize}
If \(X_0\) denotes the embedded token sequence, then
\[
X_0 \in \mathbb{R}^{B \times T \times d_{\text{model}}},
\]
where \(B\) is the batch size and \(T\) is the sequence length.

\subsection{How vectors, ``nodes'', and weight matrices should be interpreted}

It is useful to connect the usual neural-network picture of nodes and edges to the
actual arrays stored in the repository. A token representation
\[
x=(x_1,\ldots,x_{d_{\mathrm{model}}})
\]
can be pictured as a row of $d_{\mathrm{model}}$ scalar nodes. A learned linear
map does not store explicit graph edges. Instead, all connection weights are
stored in one matrix. For
\[
y=xW,\qquad W\in\mathbb{R}^{d_{\mathrm{in}}\times d_{\mathrm{out}}},
\]
the scalar output node $y_j$ is
\[
y_j=\sum_{i=1}^{d_{\mathrm{in}}}x_iW_{ij}.
\]
Thus $W_{ij}$ is exactly the weight of the connection from input feature $i$ to
output feature $j$. In the code, opening \texttt{W.data} exposes this complete
matrix directly.

There are two conceptually different kinds of coupling in a Transformer:
\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Feature coupling:} matrices such as $W_Q$, $W_K$, $W_V$,
    $W_O$, $W_{\mathrm{gate}}$, and $W_{\mathrm{up}}$ mix coordinates inside one
    token representation.
    \item \textbf{Token-to-token coupling:} the attention matrix $P$ mixes
    information between different sequence positions. It is not a learned
    parameter; it is recomputed from the current queries and keys for every input.
\end{itemize}
The feed-forward network therefore acts independently at each token position,
whereas attention is what couples different token positions.

\subsection{Transformer block: detailed structure}

A Transformer block is the repeated computational unit of the model.  In a
modern decoder-only language model, every token position carries a vector of
length $d_{\mathrm{model}}$.  For a batch of $B$ sequences of length $T$, the
input to one block is therefore
\[
X\in\mathbb{R}^{B\times T\times d_{\mathrm{model}}}.
\]
The block preserves this outer shape.  Internally, however, the vector is split
into multiple attention heads and is also temporarily expanded inside the
feed-forward or mixture-of-experts sublayer.

The block has two main residual branches:
\[
\boxed{\text{attention branch}}
\qquad\text{and}\qquad
\boxed{\text{feed-forward / MoE branch}}.
\]
A residual branch computes a transformation $F(X)$ and adds it back to the
original signal:
\[
Y=X+F(X).
\]
This means that the block can learn a correction to the existing representation
instead of replacing it completely.

\subsubsection{First normalization: RMSNorm}
The first operation is root-mean-square normalization (RMSNorm). For one token
vector $x\in\mathbb{R}^{d_{\mathrm{model}}}$,
\[
r(x)=\sqrt{\frac{1}{d_{\mathrm{model}}}\sum_{j=1}^{d_{\mathrm{model}}}x_j^2+\epsilon},
\]
\[
\widehat{x}_j=\frac{x_j}{r(x)},
\qquad
z_j=\gamma_j\widehat{x}_j.
\]
The learned parameter
\[
\gamma\in\mathbb{R}^{d_{\mathrm{model}}}
\]
rescales each component after normalization. The tensor shape remains
$B\times T\times d_{\mathrm{model}}$.

\subsubsection{Query, key and value projections}
For the normalized tensor $Z$, three learned linear maps create the query, key,
and value tensors:
\[
Q_{\mathrm{flat}}=ZW_Q,
\qquad
K_{\mathrm{flat}}=ZW_K,
\qquad
V_{\mathrm{flat}}=ZW_V.
\]
For grouped-query attention (GQA), the matrix dimensions are
\[
W_Q\in\mathbb{R}^{d_{\mathrm{model}}\times(H_Qd_h)},
\]
\[
W_K,W_V\in\mathbb{R}^{d_{\mathrm{model}}\times(H_{KV}d_h)},
\]
where
\begin{itemize}[leftmargin=1.5em]
    \item $H_Q$ is the number of query heads,
    \item $H_{KV}$ is the number of key/value heads,
    \item $d_h$ is the dimension of one attention head.
\end{itemize}
We choose
\[
H_Qd_h=d_{\mathrm{model}}.
\]
For the planned small model,
\[
d_{\mathrm{model}}=384,\qquad H_Q=6,\qquad H_{KV}=2,\qquad d_h=64.
\]
Hence
\[
W_Q\in\mathbb{R}^{384\times384},
\qquad
W_K,W_V\in\mathbb{R}^{384\times128}.
\]
After reshaping,
\[
Q\in\mathbb{R}^{B\times T\times6\times64},
\]
\[
K,V\in\mathbb{R}^{B\times T\times2\times64}.
\]

\subsubsection{What is an attention head?}
An attention head is not a separate neuron or a separate network. It is one slice
of the projected feature space.  For query head $h$, token $t$ has a vector
\[
q_{t,h}\in\mathbb{R}^{d_h}.
\]
That vector is compared with the key vectors of earlier tokens to determine how
much information should be read from their value vectors.

With GQA, several query heads share one key/value head.  In the proposed
configuration the mapping is
\[
(Q_0,Q_1,Q_2)\longrightarrow(K_0,V_0),
\]
\[
(Q_3,Q_4,Q_5)\longrightarrow(K_1,V_1).
\]
This reduces the size of the key-value cache during generation while preserving
multiple query heads.

\subsubsection{Rotary positional embedding (RoPE)}
Attention by itself does not know token order. Rotary positional embedding (RoPE)
encodes position by rotating pairs of coordinates of the query and key vectors.
For one coordinate pair,
\[
\begin{bmatrix}q'_{2i}\\q'_{2i+1}\end{bmatrix}
=
\begin{bmatrix}
\cos\theta_{t,i} & -\sin\theta_{t,i}\\
\sin\theta_{t,i} & \cos\theta_{t,i}
\end{bmatrix}
\begin{bmatrix}q_{2i}\\q_{2i+1}\end{bmatrix}.
\]
The same transformation is applied to $K$.  In the implementation this rotation
is performed directly on coordinate pairs rather than by constructing a large
block-diagonal matrix, although a debug function can materialize that matrix for
inspection.

\subsubsection{Causal attention scores}
For one query head, the raw attention score between query token $t$ and key token
$s$ is
\[
S_{t,s}=\frac{q_t^\top k_s}{\sqrt{d_h}}.
\]
The factor $1/\sqrt{d_h}$ prevents the dot products from becoming excessively
large as the head dimension grows.

Because this is an autoregressive decoder, token $t$ must not see future token
$s>t$. We therefore add a causal mask $M$:
\[
M_{t,s}=\begin{cases}
0, & s\le t,\\
-\infty, & s>t.
\end{cases}
\]
The normalized attention weights are
\[
P_{t,s}=\mathrm{softmax}_s(S_{t,s}+M_{t,s}).
\]
Thus every row of $P$ sums to one, but only over the current and previous tokens.

For all heads and batches the score tensor has shape
\[
S,P\in\mathbb{R}^{B\times H_Q\times T\times T}.
\]
This $T\times T$ object is the main reason ordinary full attention has quadratic
memory and compute scaling with sequence length.

\subsubsection{Reading information through the value vectors}
The attention probability matrix is used to form a weighted average of the value
vectors:
\[
C_{t,h}=\sum_{s\le t}P_{h,t,s}v_{s,h}.
\]
After all query heads are concatenated,
\[
C_{\mathrm{flat}}\in\mathbb{R}^{B\times T\times(H_Qd_h)}
=
\mathbb{R}^{B\times T\times d_{\mathrm{model}}}.
\]
The attention output projection is
\[
A=C_{\mathrm{flat}}W_O,
\qquad
W_O\in\mathbb{R}^{d_{\mathrm{model}}\times d_{\mathrm{model}}}.
\]
The first residual update is therefore
\[
X'=X+A.
\]

\subsubsection{Second normalization}
The second branch begins with another RMSNorm:
\[
Z_2=\mathrm{RMSNorm}(X').
\]
From here the model can use either a dense feed-forward network or a sparse
mixture-of-experts feed-forward network.

\subsubsection{Dense SwiGLU feed-forward path}
In the dense baseline every token passes through the same feed-forward matrices:
\[
G=Z_2W_{\mathrm{gate}},
\qquad
U=Z_2W_{\mathrm{up}},
\]
\[
H=\mathrm{SiLU}(G)\odot U,
\]
\[
F=HW_{\mathrm{down}}.
\]
Here $\odot$ denotes elementwise multiplication and SiLU denotes the sigmoid
linear unit activation,
\[
\mathrm{SiLU}(x)=x\,\sigma(x).
\]
For feed-forward width $d_{\mathrm{ff}}$,
\[
W_{\mathrm{gate}},W_{\mathrm{up}}
\in\mathbb{R}^{d_{\mathrm{model}}\times d_{\mathrm{ff}}},
\]
\[
W_{\mathrm{down}}
\in\mathbb{R}^{d_{\mathrm{ff}}\times d_{\mathrm{model}}}.
\]
For the proposed model, $d_{\mathrm{ff}}=1024$.
The second residual update is
\[
Y=X'+F.
\]

\subsubsection{Sparse mixture-of-experts replacement}
In the MoE version, the attention branch is unchanged. Only the dense feed-forward
path is replaced.  Instead of using one SwiGLU network for every token, the model
contains several SwiGLU experts:
\[
E_0,E_1,\ldots,E_{N_E-1}.
\]
Each expert has its own matrices
\[
W_{\mathrm{gate}}^{(e)},\quad
W_{\mathrm{up}}^{(e)},\quad
W_{\mathrm{down}}^{(e)}.
\]
A router chooses which experts process each token.  The router is simply another
learned matrix
\[
W_R\in\mathbb{R}^{d_{\mathrm{model}}\times N_E}.
\]
For one normalized token vector $z$,
\[
r=zW_R\in\mathbb{R}^{N_E}
\]
contains one routing logit per expert.  A softmax gives routing probabilities
\[
p_e=\frac{\exp(r_e)}{\sum_j\exp(r_j)}.
\]

For the planned model,
\[
N_E=6,\qquad k=2,
\]
so only the two highest-probability experts are selected for a token.  For example,
if
\[
p=[0.03,\;0.12,\;0.51,\;0.07,\;0.23,\;0.04],
\]
then experts 2 and 4 are selected. Their selected probabilities are renormalized:
\[
\widetilde p_2=\frac{0.51}{0.51+0.23},
\qquad
\widetilde p_4=\frac{0.23}{0.51+0.23}.
\]
The sparse feed-forward output becomes
\[
F_{\mathrm{MoE}}(z)
=
\widetilde p_2E_2(z)+\widetilde p_4E_4(z).
\]
The other experts do not evaluate this token. This is the source of sparse
conditional computation: the model owns many parameters, but only a subset is
active for a given token.

The second residual update becomes
\[
Y=X'+F_{\mathrm{MoE}}(Z_2).
\]

\subsubsection{Optional shared expert}
A later variant will add a shared expert that is always active:
\[
F_{\mathrm{MoE}}(z)
=E_{\mathrm{shared}}(z)
+\sum_{e\in\mathrm{TopK}(p)}\widetilde p_eE_e(z).
\]
The shared expert can represent transformations useful to most tokens, while the
routed experts are free to specialize.

\subsubsection{How the top-k selection is differentiated}
The expert indices selected by top-$k$ are discrete. During the local backward
pass, the selected expert identities are treated as fixed and gradients propagate
through:
\begin{itemize}[leftmargin=1.5em]
    \item the selected expert outputs,
    \item their selected routing weights,
    \item and therefore the router logits that produced those weights.
\end{itemize}
At the exact point where two experts exchange rank, the top-$k$ selection is
non-smooth. This is important when performing finite-difference checks: a numerical
perturbation that changes the selected expert set can cross a genuine routing
boundary.

\subsubsection{Why load balancing is required}
Without additional control, a router can collapse and send most tokens to only a
few experts. We will therefore record for each expert:
\[
N_e=\text{number of routed tokens},
\]
as well as routing probabilities and entropy. The first MoE implementation will
use a conventional auxiliary balancing objective; a later version can test
bias-based or auxiliary-loss-free balancing. The point of the repository is to
make these choices measurable rather than hidden.

\subsubsection{Dense and MoE blocks have the same external shape}
Importantly, both variants map
\[
\mathbb{R}^{B\times T\times d_{\mathrm{model}}}
\longrightarrow
\mathbb{R}^{B\times T\times d_{\mathrm{model}}}.
\]
Therefore the rest of the decoder stack does not need to know whether the second
branch is dense or sparse. This allows the repository to implement both versions
behind a common block interface and compare them directly.


\subsubsection{Tensor-shape trace for the planned model}
For $d_{\mathrm{model}}=384$, $H_Q=6$, $H_{KV}=2$, $d_h=64$,
$d_{\mathrm{ff}}=1024$, $N_E=6$, and $k=2$, the main tensors inside one block are:

\begin{center}
\small
\begin{tabular}{p{0.27\linewidth} p{0.29\linewidth} p{0.36\linewidth}}
\toprule
\textbf{Quantity} & \textbf{Shape} & \textbf{Role} \\
\midrule
Block input $X$ & $B\times T\times384$ & Current representation of every token. \\
Normalized input $Z_1$ & $B\times T\times384$ & Input to attention. \\
Queries $Q$ & $B\times T\times6\times64$ & Six query heads per token. \\
Keys/values $K,V$ & $B\times T\times2\times64$ & Two shared key/value heads. \\
Logical GQA-expanded $K,V$ & $B\times T\times6\times64$ & Each key/value head serves three query heads. \\
Scores/probabilities $S,P$ & $B\times6\times T\times T$ & Causal token-to-token attention matrices. \\
Head context $C$ & $B\times T\times6\times64$ & Weighted sums of value vectors. \\
Merged attention output & $B\times T\times384$ & Concatenated attention heads. \\
Dense SwiGLU $G,U,H$ & $B\times T\times1024$ & Expanded per-token feature space. \\
Dense FFN output $F$ & $B\times T\times384$ & Returned to the residual stream. \\

\end{tabular}
\end{center}

The first implementation will \textbf{not drop tokens because of expert capacity}.
Every top-$k$ assignment will be evaluated. This keeps routing transparent; expert
capacity limits and token dropping can be studied later as separate systems-level
optimizations.

\subsection{Stacking}
If there are \(L\) layers, the sequence passes through:
\[
X_0 \rightarrow X_1 \rightarrow X_2 \rightarrow \cdots \rightarrow X_L.
\]

\subsection{Final normalization and logits}
After the last block:
\[
Z_{\text{final}} = \mathrm{RMSNorm}(X_L).
\]
The logits are then computed using the tied embedding matrix:
\[
\text{logits} = Z_{\text{final}} E^\top.
\]

\subsection{Next-token prediction}
For each position \(t\), the model predicts the next token:
\[
p(x_{t+1}\mid x_{\le t}) = \mathrm{softmax}(\text{logits}_t).
\]
Training uses the mean cross-entropy loss over all positions.

\section{Numerical conventions and initialization}

The initial implementation uses:
\begin{itemize}[leftmargin=1.5em]
    \item clipped normal initialization for most matrices,
    \item smaller standard deviation for residual-output matrices,
    \item \(\gamma = 1\) for RMSNorm gains,
    \item AdamW optimization,
    \item global gradient clipping,
    \item warmup and cosine learning-rate decay.
\end{itemize}

The main reason is not fashion; it is numerical stability and interpretability.
A transparent project is easier to debug when:
\begin{itemize}[leftmargin=1.5em]
    \item activation scales are monitored,
    \item gradient scales are monitored,
    \item the optimizer is simple and explicit,
    \item and each matrix has a clear role.
\end{itemize}

\section{How training will be validated}

Before any serious training run, the repository should verify:

\begin{enumerate}[leftmargin=1.5em]
    \item \textbf{Operator checks:} each layer passes local finite-difference checks.
    \item \textbf{Block checks:} a full Transformer block passes directional derivative checks.
    \item \textbf{Model checks:} the full dense model passes end-to-end gradient tests on a tiny example.
    \item \textbf{Memorization checks:} the model can intentionally overfit a tiny corpus.
    \item \textbf{Scaling checks:} only after the above are correct do we train on larger corpora.
\end{enumerate}

\section{MoE design planned for this repository}

The first complete language model will be dense because it is easier to verify.
Once that implementation can overfit a tiny corpus and passes end-to-end gradient
checks, the dense SwiGLU branch will be replaced by a mixture-of-experts (MoE)
branch while leaving the attention sublayer unchanged.

\subsection{Initial MoE configuration}
The initial target configuration is:
\[
N_E=6\ \text{routed experts},\qquad k=2,
\]
with one optional shared expert added in a later experiment. Each routed expert is
itself a complete SwiGLU feed-forward network.

For every token, the router performs the following sequence:
\[
z\in\mathbb{R}^{d_{\mathrm{model}}}
\xrightarrow{\;W_R\;}
r\in\mathbb{R}^{N_E}
\xrightarrow{\;\mathrm{softmax}\;}
p
\xrightarrow{\;\mathrm{top}\mbox{-}k\;}
\{e_1,\ldots,e_k\}.
\]
The selected probabilities are renormalized and used as mixture coefficients.
Consequently, a token can use different feed-forward parameters from another token
in the same sequence and even from another position in the same sentence.

\subsection{Token-to-expert dispatch}
For a batch containing $B T$ token representations, the implementation will first
flatten the token dimensions:
\[
Z\in\mathbb{R}^{(BT)\times d_{\mathrm{model}}}.
\]
The router then computes
\[
R=ZW_R\in\mathbb{R}^{(BT)\times N_E}.
\]
After top-$k$ selection, each token has an integer expert-index vector and a
floating-point routing-weight vector. Conceptually:
\[
\text{token }i\longrightarrow
\big[(e_{i,1},\widetilde p_{i,1}),\ldots,(e_{i,k},\widetilde p_{i,k})\big].
\]
Tokens assigned to expert $e$ are gathered into a temporary expert batch, processed
by that expert, multiplied by the corresponding routing weights, and scattered
back into their original token locations. If a token is sent to two experts, two
weighted contributions are accumulated at the same output location.

\subsection{What will be inspected}
The repository will explicitly expose:
\begin{itemize}[leftmargin=1.5em]
    \item the router matrix $W_R$,
    \item router logits for each token,
    \item routing probabilities,
    \item selected expert indices,
    \item number of tokens handled by each expert,
    \item routing entropy,
    \item gradient norms for each expert,
    \item and expert activation statistics by data domain.
\end{itemize}
Because dataset metadata will retain whether a document came from prose, code,
mathematics, or synthetic educational data, we will eventually be able to measure
quantities such as
\[
P(\text{expert }e\mid\text{code})
\quad\text{and}\quad
P(\text{expert }e\mid\text{mathematics}).
\]
This provides a direct way to test whether the experts actually specialize.

\subsection{Dense versus sparse comparison}
A central research comparison will hold the approximate active computation per
token roughly fixed while increasing the total number of available parameters in
the MoE model.  We will then compare:
\begin{itemize}[leftmargin=1.5em]
    \item training loss versus tokens seen,
    \item validation loss and perplexity,
    \item wall-clock throughput,
    \item active floating-point operations per token,
    \item router balance,
    \item and expert specialization.
\end{itemize}

\section{Conclusion}

This repository is intended to become a transparent experimental platform for
understanding the full life of a language model:

\begin{center}
raw text $\rightarrow$ tokens $\rightarrow$ embeddings $\rightarrow$ Transformer blocks
$\rightarrow$ logits $\rightarrow$ cross-entropy loss $\rightarrow$ gradients
$\rightarrow$ weight updates.
\end{center}

The project starts with dense explicit components, validates them carefully, and only
then moves toward modern sparse mechanisms such as MoE routing and expert specialization.
